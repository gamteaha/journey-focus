# 근경 이동 중 프레임 지연 조사 · 2026-11-03

일반 개발용 PC의 Chrome headless/전용 QA 프로필에서 같은 300m, 30초 경로를 한 탭으로 실행했다. CPU 샘플링과 가벼운 호출 집계를 켠 관측이며 실제 사용자 GPU의 성능 보장이나 엄밀한 반복 벤치마크는 아니다. 지형 캐시/렌더 상황은 실행마다 다를 수 있다.

## 원인과 변경

초기 프로필의 약 31.6초 중 `globe.getHeight` 집계 시간이 약 21.5초였다. 타일 완료 이벤트 34회마다 식생 원점과 주택 대지 약 153지점을 한꺼번에 조회했고, 카메라도 중앙을 중복 포함한 8지점을 초당 약 10번 조회했다. CPU 표본에서도 SDK의 ray/triangle 교차 계산이 큰 비중이었다. `camera.setView` 자체는 전체 약 56ms였다.

- 타일 완료 이벤트는 작업을 예약만 한다. 근경 높이 보정은 가까운 개체부터 애니메이션 프레임으로 분산한다.
- 한 프레임에 작업 예산 4ms 또는 최대 4단계를 처리한다. SDK의 한 번의 조회가 예산보다 오래 걸리는 것은 중간에 중단할 수 없다.
- 진행 중 새 이벤트는 합쳐서 다음 한 번의 보정으로 처리한다. 모드를 닫거나 오류가 나면 예약과 진행 작업을 취소한다.
- 높이/기초 크기/표시 상태가 변하지 않은 주택은 모델 행렬과 엔티티를 다시 쓰지 않는다.
- 재생 중 카메라는 12m 범위의 5지점을 5Hz로 조회하고, 매 프레임 높이를 보간한다. 초기 진입·직접 탐색·리셋은 즉시 정렬한다. 기존 중앙 중복 조회도 제거했다.
- 소나무는 원본 재질을 유지한 경량 메시로 교체했다. 이는 별도 형상/메모리 예산 개선이며, 아래 결과만으로 나무 경량화가 특정 지연 감소의 원인이라고 단정하지 않는다.

## 관측 결과

| 단계 | getHeight 호출 | 조회 집계 시간 | 프레임 간격 95백분위 | 최대 간격 |
| --- | ---: | ---: | ---: | ---: |
| 한 번에 근경 재조회 | 8,851 | 21,477ms | 35.4ms | 407.9ms |
| 프레임 분산 + 주택 변경 감지 | 7,816 | 18,951ms | 40.4ms | 66.4ms |
| 위 변경 + 경량 소나무 | 7,809 | 18,917ms | 40.1ms | 53.5ms |
| 위 변경 + 카메라 조회 감소 | 7,132 | 17,873ms | 28.7ms | 43.3ms |

프레임을 나눈 첫 단계에서는 가장 긴 정지가 줄어드는 대신 일반 프레임에 작은 작업이 나뉘어 들어갔다. 최종 관측에서는 95백분위와 최대 간격 모두 낮아졌다. 실시간 FPS가 높아지면 SDK 자체 갱신 횟수도 늘어나므로 총 호출 수가 카메라 샘플 감소 비율만큼 줄어들지는 않는다. 모든 설정/기기에서 같은 결과를 보장하지 않는다.

기록: [기존](performance-profile-balanced.json), [프레임 분산](performance-profile-balanced-staggered.json), [경량 소나무](performance-profile-balanced-lod.json), [카메라 보정](performance-profile-balanced-camera.json).

원시 SDK 코드나 API 키를 내보내지 않고 함수명·키 없는 URL 경로·시간 집계만 저장했다. 지형 표고 원본 시계열은 저장하지 않는다. 높이 이동/지면 거리 검사는 별도의 `measure-motion.mjs`로 수행하며, 이 진단은 프레임마다 추가 높이 조회를 하므로 순수 재생 성능과 동일하게 해석하지 않는다.
